Overview

MedBiquitous Healthcare LOM at a glance

What is Healthcare LOM?

The MedBiquitous Healthcare Learning Object Metadata standard (Healthcare LOM, ANSI/MEDBIQ LO.10.1-2008, v1.1 of 30 September 2009) describes healthcare and medical education content — courses, CME activities, simulations, images and other learning objects — so that it can be cataloged, searched, shared and accredited.

It is an application profile of the IEEE Learning Object Metadata standard (IEEE 1484.12.1, XML binding 1484.12.3): every Healthcare LOM document is a valid IEEE LOM record with nine standard categories, plus the hx:healthcareMetadata extension for continuing-education credits, target audiences, disclosures and medical image descriptors, healthcare vocabularies for four LOM elements, and attributes for clinical terminology keywords (MeSH, SNOMED, UMLS).

Categories & elements

The nine IEEE LOM categories and their elements

Category 1

General <general>

#ElementDescription
1.1identifierA globally unique label that identifies this learning object: a catalog (identification scheme, e.g. URI, ISBN, DOI) and an entry within it.
1.2titleName given to this learning object.
languageThe primary human language used, as a language tag such as en-US or fr (ISO 639 language, optional ISO 3166 country).
1.4descriptionA textual description of the content of this learning object.
1.5keywordA keyword or phrase describing the topic of this learning object. HLOM use the Source and ID columns to reference a clinical terminology such as MeSH, SNOMED or UMLS (e.g. MeSH D009203).
1.6coverageThe time, culture, geography or region to which this learning object applies.
1.7structureUnderlying organizational structure of this learning object.
1.8aggregationLevelThe functional granularity of this learning object (1 = raw media, 4 = largest, e.g. a course or set of courses).
Category 2

Life Cycle <lifeCycle>

#ElementDescription
2.1versionThe edition of this learning object.
2.2statusThe completion status or condition of this learning object.
2.3contributeEntities (people, organizations) that have contributed to the state of this learning object during its life cycle. HLOM use the date of the publisher's contribution as release date and the reviewer's as review date.
roleKind of contribution. HLOM adds the roles reviewer, programmer, producer, director and other.
entityThe contributing person or organization, as a vCard (BEGIN:VCARD ... END:VCARD).
dateThe date of the contribution (YYYY, YYYY-MM-DD or YYYY-MM-DDThh:mm:ss with optional time zone).
Category 3

Meta-Metadata <metaMetadata>

#ElementDescription
3.1identifierA globally unique label that identifies this metadata record.
3.2contributeEntities that have affected the state of this metadata record (creator, validator).
3.3metadataSchemaThe metadata specifications this record conforms to. HLOM requires LOMv1.0 and HEALTHCARE_LOMv1 (and SCORM_CAM_v1.3 if applicable).
3.4languageLanguage of this metadata record; the default for strings without a language attribute.
Category 4

Technical <technical>

#ElementDescription
4.1formatTechnical data type(s) of the components of this learning object, as MIME types (or "non-digital").
4.2sizeThe size of the digital learning object in bytes.
4.3locationA string (usually a URL) used to access this learning object.
4.4requirementThe technical capabilities necessary for using this learning object. All conditions of a requirement are alternatives (OR).
4.5installationRemarksDescription of how to install this learning object.
4.6otherPlatformRequirementsInformation about other software and hardware requirements.
4.7durationTime a continuous learning object takes when played at intended speed, as an ISO 8601 duration such as PT1H30M.
Category 5

Educational <educational>

Key educational or pedagogic characteristics of this learning object. A record may describe several educational uses.

Section 2.1 · spec p.18

healthcareMetadata

healthcareMetadata is the root element. It contains metadata specific to healthcare education. healthcareMetadata must occur once if Healthcare LOM is being used. healthcareMetadata has the subelements healthcareEducation, which describes healthcare metadata for educational offerings, and healthcareAsset, which describes healthcare specific metadata for images, multimedia files, and other types of assets. The uniqueElementName attribute ensures that only one instance of healthcareMetadata occurs in a Healthcare LOM document.

Section 2.7

LanguageString

Many of the elements in Healthcare LOM use the LanguageString datatype from the IEEE LOM standard. LanguageString provides a way for LOM document creators to specify a value for an element in multiple languages. For example, document creators can specify a single keyword term in both French and English. Within the healthcare extensions, the faculty disclosure description can be encoded multiple languages, too. This functionality is important for those creating educational resources for a multilingual population. Elements using the LanguageString datatype have the subelement of string, which is described in the following table.

ElementMultiplicityDatatypeDescription
stringOptional0 or moreCharacterStringstring is the subelement of any element using the LanguageString datatype. It provides a word or phrase in a human language. If the string element is repeated within a particular element, each value should be semantically equivalent, such as a translation or alternative description.
string/@language(optional)0 or 1language codelanguage specifies the human language of the text string. If the language attribute is not present, the language will be determined by the value of the language element within the LOM metaMetadata container. Valid values are codes from the ISO-10646-1 standard. For example, en for English and fr for French.

Note: string is in the LOM namespace (unprefixed in samples), even inside hx: elements. (Spec error: language codes are ISO 639 / RFC 1766-style tags, not ISO-10646-1.)

Section 2.8

CharacterString

Many of the elements and attributes in Healthcare LOM use the CharacterString data type from the IEEE LOM standard. CharacterString indicates that the data value for the element or attribute is a character string but is NOT a word or phrase in a human language. For example, a name would be encoded using the CharacterString data type. The characters represented by this data type are from the ISO/IEC 10646-1:2000 standard. This ISO standard, also known as UCS, attempts to include all characters used in all written languages in the world. CharacterString uses the XML string data type.

Custom attributes · spec p. 37

Clinical terminology keywords

Medical terminologies such as MeSH, SNOMED and UMLS provide a structure for describing healthcare topics and can facilitate indexing, cataloging and discovery of healthcare learning content. Healthcare LOM adds two attributes to the LOM keyword element:

Element / attributeDescription
keywordkeyword is the subelement of general. Its subelements provide common keywords (important concepts or topics) that describe the educational offering.
keyword/@hx:sourcesource specifies the terminology or vocabulary from which the keyword is taken. For example, UMLS, SNOMED, or MeSH.
keyword/@hx:idid defines the unique identifier associated with this term in the structured terminology or vocabulary. For example, D009203.
XML<keyword hx:source = "MeSH" hx:id = "D009203">
   <string language = "en">myocardial infarction</string>
</keyword>

Tip — On the General page, look up MeSH descriptors to fill the term, hx:source and hx:id in one step.

spec pp. 40-41

Custom elements

  • "Healthcare LOM allows organizations to add new elements to those described in this document and in the IEEE LOM documentation."
  • Adding Elements to Existing LOM Categories: "Healthcare LOM allows extensions to general, lifecycle, metaMetadata, technical; educational, rights, relation, annotation, classification, and any of their sub-elements that are also container elements." (per IEEE 1484.12.3)
  • Adding Elements to a New Category: "Healthcare LOM defines a sub-element of lom called customElements. The customElements container may contain any new elements or new categories of elements as long as those elements are qualified by an XML namespace. Healthcare LOM does not permit extensions to healthcareMetadata or its subelements, so any new elements specific to healthcare should be placed in the customElements container."
  • hx:customElements is in the hx namespace, child of lom.

Conformance checklist

What makes a document a valid Healthcare LOM instance

spec p. 42 · verbatim

Conformance

To be a conformant instance of Healthcare LOM, an XML document:

  • Shall validate against the Healthcare LOM (ANSI /MEDBIQ LO.10.1-200x) XML schema available at http://ns.medbiq.org/lom/extend/v1/healthcarelom.zip
  • Shall be a conforming XML instance of LOM as defined by IEEE Standard for Learning Technology--Extensible Markup Language (XML) Schema Definition Language Binding for Learning Object Metadata (IEEE 1484.12.3)
  • Shall conform to the Additional Requirements stated in this document
  • May include elements not defined in this document or in the IEEE Standard for Learning Technology--Extensible Markup Language (XML) Schema Definition Language Binding for Learning Object Metadata (IEEE 1484.12.3) by using the customElements container defined in the section Custom Elements.

Additional requirements

The metadata document must indicate that it is conformant with the LOM version 1.0, SCORM Content Aggregation Model version 1.3 (if applicable), and Healthcare LOM version 1 standards. To indicate this conformance, include the following XML code in the metaMetadata section of the metadata record:

XML<metadataSchema>LOMv1.0</metadataSchema>
<metadataSchema>SCORM_CAM_v1.3</metadataSchema>
<metadataSchema>HEALTHCARE_LOMv1</metadataSchema>

SCORM_CAM_v1.3 is only required for SCORM content packages.

What the editor checks

The Validation view combines XML Schema validation, model constraints and the specification's requirements. Errors make a document non-conformant; warnings and infos point to likely mistakes and best practices.

Known issues in the specification

Checked against xsd/healthcare/healthcaremetadata.xsd: all restricted types are xsd:restriction base="xsd:string" enumerations, so leading/trailing whitespace is NOT collapsed and makes the value invalid.

Sample 8.1 (will NOT validate as printed):

  • <hx:creditUnit>Credits</hx:creditUnit> – "Credits" is not in creditUnitType (valid: Credit).
  • <hx:participationModality> with surrounding newlines/indentation – invalid against the enum (should be technology based with no whitespace).
  • <hx:relevantFinancialRelationship> with surrounding whitespace – invalid against yesNoType (should be no).
  • AAFP Prescibed – typo for "AAFP Prescribed" (free CharacterString, so valid but wrong).
  • hx:accreditedProvider value has surrounding whitespace (valid, CharacterString, but should be trimmed).
  • application/http is not a real MIME type (LOM format is CharacterString, so schema-valid).
  • vCard entities lack a newline before END:VCARD and lack VERSION (not valid vCard, schema-valid).
  • Same printed sample in the body text, p.23 (healthcareEducation example), uses "MedBiquitous gratefully acknowledges..." and contact Edgar Allan Poe, eapoe@medbiq.org, mixes prefixed/unprefixed hx elements; it's an illustrative fragment, not a fixture.

Sample 8.2:

  • hx:relevantFinancialRelationship with surrounding whitespace – invalid against yesNoType.
  • participationModality here is a visual wrap -> technology based (valid). If a raw newline were kept it would be invalid.
  • AMA PRA category 1 – recommended value is "AMA PRA Category 1" (case; free text, schema-valid).
  • metaMetadata identifier http://www.cd.gov/metadata/001 – probably a typo for cdc.gov.
  • technical/location contains a trailing newline+spaces inside the URL value.
  • ANCC credits block has no activityCertification (fine).

Sample 8.3:

  • image/jpg – registered MIME type is image/jpeg.
  • xsi:schemaLocation value has a trailing space (harmless).
  • general/identifier/entry has surrounding whitespace inside the URL.
  • metadataSchema omits SCORM_CAM_v1.3 (allowed: "if applicable").

Body-text examples (not appendix) – noted errors:

  • p.31 activityLocation example uses prefix a: with no namespace declaration; StreetAddressLine wraps.
  • p.34 healthcareAsset example: <medicalImageType> radiograph</medicalImageType> has a leading space (invalid vs enum), unprefixed hx elements, and typographic quotes language=”en”.
  • p.35 LanguageString example uses language = "sp" for Spanish; correct ISO 639 code is es.
  • p.37 keyword example has a curly closing quote on "D009203”.
  • p.41 customElements example is missing </lom>.

Other spec inconsistencies: keyword multiplicity printed as "0 or 1" (LOM: 0..); room/building multiplicity printed "1" while Required = Optional (local XSD: minOccurs=0, i.e. 0..1); nonAccreditedProvider "0 or more" in table vs "?" in diagram (local XSD: 0..unbounded); readingLevel "0 or 1" in table vs "" in diagram (local XSD: 0..unbounded); LanguageString language codes attributed to "ISO-10646-1" (wrong standard); common/rootElement and vocabValues listed without .xsd.

Typos in the requirements table: CommercialSupport -> commercialSupport; CommercialSupportAcknowledgement -> commercialSupportAcknowledgement; relevantfinancialRelationshipDisclosure -> relevantFinancialRelationshipDisclosure; offLableDescription -> offLabelDescription; lifecycle -> lifeCycle; taxonpath -> taxonPath.

Health professions

Following are recommended terms for health professions and health specialties that should capture the needs of most health professions educators. They are intended to provide guidance for those organizations seeking to describe the professional audience for an educational offering in a consistent manner. The list of professionals is adapted from a list created by the US Health Resources and Services Administration. The list of health specialties is adapted from specialties and internal medicine/pediatric subspecialties as recognized by the Accreditation Council on Graduate Medical Education and the American Board of Medical Specialties. These lists may not be adequate to meet the needs of hospitals and large healthcare organizations requiring a highly detailed hierarchical list of professions. More detailed lists of healthcare professionals have been defined by HL7, SNOMED, the US Health Resources and Services Administration, the US Office of Program Management, and the National Center of Educational Statistics (Classification of Instructional Programs). How to

Create a document from a template

  1. Choose File › New › Healthcare LOM Document (Ctrl+N).
  2. Pick a template — e.g. a CME course, a live activity or a medical image asset — and enter the title and the language of the record.
  3. The new record already contains LOMv1.0 and HEALTHCARE_LOMv1 metadata schemas and the healthcareMetadata container. If enabled in the preferences, you are added as author and as meta-metadata creator.
  4. Fill the form pages; every field explains itself in a tooltip, and F1 opens its topic in this guide.
How to

Add MeSH keywords

  1. Open the General page and go to Keywords.
  2. Search the National Library of Medicine MeSH vocabulary by term; pick a descriptor from the results.
  3. The keyword is written with hx:source="MeSH" and the descriptor ID, e.g. hx:id="D009203".
  4. MeSH lookup needs internet access; it can be disabled or pointed to another server in Window › Preferences › Healthcare LOM › MeSH.
How to

Validate a document

  1. Problems are listed in the Validation view; by default the document is validated a moment after each change (see Preferences › Validation).
  2. Click Validate in the tool bar to validate the active document on demand.
  3. Double-click a problem to jump to the element; errors make the document non-conformant, warnings and infos point to likely mistakes and best practices.
How to

Work with the XML

  1. The XML page shows the document source with syntax highlighting.
  2. Edits are applied to the model when you leave the page or save; files that cannot be fully loaded open with their original text so you can repair them.
  3. The Tree page and the Outline and Properties views show the complete structure, including custom extension elements.
How to

Organize your library

  1. The library collects the Healthcare LOM documents in your library folder (Preferences › Healthcare LOM).
  2. Search and filter records by title, keyword, credit type or audience and open them with a double-click.
How to

Set your preferences

  1. Open Window › Preferences.
  2. Healthcare LOM — default language of new documents, your name, organization and email (written as a vCard), and the library folder.
  3. Validation — validate while typing, the delay, and whether informational hints are shown.
  4. MeSH — enable the lookup and set the server address.

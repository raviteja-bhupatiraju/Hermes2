MedBiquitous Virtual Patient

MedBiquitous Virtual Patient (MVP) 1.0, ANSI/MEDBIQ VP.10.1-2010, is the MedBiquitous standard for exchanging and reusing virtual patients: "interactive computer simulations of real-life clinical scenarios for the purpose of medical training, education, or assessment". A virtual patient is a package of three XML documents, media files and a manifest; Hermes 2 edits and checks the three documents.

The parts of a virtual patient

The specification defines five components. A virtual patient package (a SCORM 2004 4th Edition content package, one virtual patient per package) holds them in fixed files:

ComponentFileHoldsHermes document type
Virtual Patient Data (VPD)virtualpatientdata.xmlThe clinical and demographic data: demographics, narrative texts, interview items, physical exams, diagnostic tests, diagnoses, interventions, medicationsVirtual Patient Data 1.0
Data Availability Model (DAM)dataavailabilitymodel.xmlGroups (DAM nodes) of VPD data and media that are shown together, and when each item is displayedVirtual Patient Data Availability Model 1.0
Activity Model (AM)activitymodel.xmlWhat the learner can do: activity nodes, the links between them, counters, timers and rulesVirtual Patient Activity Model 1.0
Media Resources (MR)any, listed in imsmanifest.xmlImages, video, audio, documents, each with a resource identifier in the manifest(edited outside Hermes)
Playeran HTML launch pageThe functional specification of conformant players (not a document)

All content lives in the VPD or in media resources. The Activity Model refers only to DAM nodes, and the DAM refers to the data and media, always with XPath expressions:

  • an activity node shows a DAM node: /DataAvailabilityModel/DAMNode[@id='dam-history'];
  • a DAM node item points to VPD data, by id or by a unique path: /VirtualPatientData/InterviewItem[@id='i1'], /VirtualPatientData/PatientDemographics/CoreDemographics/Name/text();
  • or to a media resource of the manifest: /manifest/resources/resource[@identifier='r-ecg'];
  • links and rules refer to activity nodes: /ActivityModel/ActivityNodes/NodeSection/ActivityNode[@id='n-start'].

Virtual Patient Data

The root element VirtualPatientData (namespace http://ns.medbiq.org/virtualpatientdata/v1/) contains, in this order: PatientDemographics, VPDText, Medication, InterviewItem, PhysicalExam, DiagnosticTest, Diagnosis, Intervention, Organization and XtensibleInfo. Every data element has an id by which the DAM selects it.

Editor pageElements
PatientPatientDemographics: CoreDemographics (name, patient ID, age as a duration such as P58Y, sex, race, species, breed) and DemographicCharacteristics
NarrativeVPDText: chief complaint, history, problem, allergy or narrative texts. The text is a restricted XHTML div (paragraphs, lists, headings, tables, images, links, and the MVP media element that refers to a resource of the manifest); it is edited on the XML page.
HistoryInterviewItem (question and response) and Medication (name, dose, route, frequency)
Physical ExamPhysicalExam: exam, location on the body, action, finding, description
Diagnostic TestsDiagnosticTest: test name, unit, result, normal range
DiagnosesDiagnosis: differential diagnoses with a likelihood; the author's final diagnosis has authorDiagnosis="true"

The title of a VPD document is the patient's name (or patient ID).

Data Availability Model

The root element DataAvailabilityModel (namespace http://ns.medbiq.org/dataavailabilitymodel/v1/) holds one or more DAMNodes. A DAM node has an id, an optional label for authors and one or more DAMNodeItems. An item has:

  • ItemPath: the VPD element or media resource it shows;
  • display: immediately (the default), ontrigger (after a learner interaction), delayed or ifrequested (only if the learner asked for it, such as an ordered test);
  • optionally ItemComment (a DAM node with feedback shown after the item is triggered), DAMNodePaths (DAM nodes included as sub-groups), ItemOrder, and AlternativePath (only for an ItemPath into XtensibleInfo).

The single editor page DAM Nodes lists the nodes and their items; the path fields offer the usual path patterns while you type. The DAM has no title element, so Hermes titles it by its number of nodes.

Activity Model

The root element ActivityModel (namespace http://ns.medbiq.org/activitymodel/v1/) contains Properties (counters and a timer), ActivityNodes (node sections containing activity nodes or further sections), Links and XtensibleInfo.

  • Activity nodes (page Activity Nodes): each node has an id, a label and a Content DAM node. "The first node in the Activity Model file is considered to be the first node in the activity"; a node with no links leaving it (or only one back to the first node) is an end node. Node rules add to or subtract from counters, allow entry only under a Boolean condition on visited nodes and triggered data (ConditionalRule), choose one leaving link at random (Probability) or make the node reachable from a navigation menu (NavigateGlobal). A node may have its own timer.
  • Links (page Links): one-way links from ActivityNodeA to ActivityNodeB with a label, a Weighting (percent) and counter actions.
  • Counters and Timer (page Counters and Timer): counters such as patient health or costs with an initial value and rules that redirect the learner or show a message at a threshold, and the timer of the whole activity.

The title of an Activity Model is the label of its first node section, which usually names the case.

Checks across the package. When a document lies in a folder with the other documents under the file names the specification prescribes, Hermes also checks the references between them: the Content of each activity node must name a DAM node of dataavailabilitymodel.xml, and every VPD path of the DAM and of condition operands must select an element of virtualpatientdata.xml. These are warnings, since the other document may still be in progress; they use the saved files. Media references (/manifest/...) are not checked.

Templates and samples

New documents of the three types start from templates: a VPD with the patient's name and a chief complaint, an Activity Model with a node section named after the case, two nodes and a link, and a DAM with two nodes pointing into that VPD. Save them as virtualpatientdata.xml, activitymodel.xml and dataavailabilitymodel.xml in one folder so that the package checks apply.

The samples (samples/virtual-patient of the MedBiquitous model bundle) are one fictional branching case, "Chest pain in a 58-year-old man": the VPD of the patient with interview, examination, ECG and troponin, diagnoses, interventions and medications; a DAM that progressively releases the data, with feedback on ordering the ECG and test results shown only if requested; and an Activity Model with two node sections, counters, a timer, a conditional rule and a branch to a good and a bad outcome.
